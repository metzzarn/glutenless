# AGENTS.md

This file provides guidance to AI coding agents working with code in this repository.

Glutenless is an Expo (SDK 57) / Expo Router app for finding gluten-free and gluten-removed beers: search, voice search, and camera scanning of cans, bottles and menus. People with coeliac disease rely on it, so **the one invariant that outranks everything else: never show a beer that contains gluten as gluten-free.** When matching or data logic is uncertain, fall back to "not in our list" or to suggestions the person confirms.

**Expo has changed since most training data.** Read the versioned docs at https://docs.expo.dev/versions/v57.0.0/ before writing code that touches Expo APIs.

## Commands

```bash
npm test                                   # Jest (jest-expo preset)
npx jest __tests__/match.test.ts           # one file
npx jest -t "generic name"                 # tests whose name matches
npm run typecheck                          # tsc --noEmit
tools/ocr-bench/install_models.sh          # once: puts the on-device OCR models and their ONNX Runtime in the app (needs the bench's .venv)
npm run build:android                      # expo prebuild + gradlew assembleRelease (arm64-v8a only)
~/Android/Sdk/platform-tools/adb install -r android/app/build/outputs/apk/release/app-release.apk
npm run stamp-data                         # after any edit to data/beers.json
node tools/merge-beers.mjs candidates.json --dry-run   # add researched beers (drop --dry-run to write)
```

`android/` and `ios/` are generated by `expo prebuild` and gitignored. Release builds are shrunk by R8 (`app.json`); a class looked up by name from native code needs a keep rule there (`extraProguardRules`, as for ONNX Runtime). Never edit them by hand; native build changes go through config plugins (see `modules/label-reader/app.plugin.js`) or `app.json`.

## Beer data

- `data/beers.json` is bundled and seeded into SQLite on launch (`lib/db.ts` `initDb`), then `lib/sync.ts` fetches the hosted copy (URLs in `app.json` `extra`) in the background. Both go through `upsertBeers`, which treats its input as the complete set (rows missing from it are deleted) and never touches the user's `favorite` or `personalNote`.
- `data/beers-version.json` stamps the list (`updatedAt` + sha256). Data is only replaced by a newer stamp, whether bundled or hosted. `__tests__/dataVersion.test.ts` fails if `beers.json` changed without `npm run stamp-data`.
- `status` is derived from `glutenFree` (`lib/status.ts`), never stored independently. Schema changes go in `TABLE_COLUMNS_DDL`/`CANONICAL_COLUMNS`; `migrateSchema` rebuilds the table on installed apps.
- Rules for editing the list are in `data/update_beers_prompt.md`: ids are permanent, never remove a beer, existing entries only ever change `discontinued`, and only add a beer with a verified gluten-free/gluten-removed claim (<20 ppm). Ingredients alone are not enough.
- `tools/confirm-beers.html` is a standalone browser tool for recording which fields were verified (`confirmed`).

## Camera recognition pipeline

`app/camera.tsx` → `lib/ocr.ts` (`scanPhoto`) → `lib/match.ts`. Photos are read by the on-device models (`modules/ocr-models`, below) where they're available, i.e. Android: a can or bottle at 960 px with WATERec, a menu at 1600 px without it (its guesses would be matched as menu entries). On iOS, or if the models fail, the platform's text recognition reads them (ML Kit, or Apple Vision on iOS). ML Kit comes from Google Play services (`plugins/withPlayServicesTextRecognition.js` swaps out the bundled library), which downloads its model once rather than the APK carrying it. A can matches on PP-OCRv6's text alone; a beer that matches only once WATERec's readings are added is shown as "Is this X?" (`PhotoScan.confirm`). For a can with no match, `lib/aiLabel.ts` (`identifyWithAi`) asks Gemini Nano to *transcribe* the label. It never asks the model to identify the beer, because a model will confidently name a look-alike. The matcher decides from the text. A Nano match counts only when both readings (1536 px and 1024 px photo) match the same beer on their own, and even then it is shown as "Is this X?" for the person to confirm. Otherwise the camera shows suggestions from a brewery that was read, flagging name words not seen on the label (most of all a missing "Gluten Free"), or the warning.

Safety rules in `lib/match.ts`, each added after a real false match:
- A brewery alone never identifies a beer; breweries also make beers with gluten.
- A name made only of style words (`STYLE_WORDS`: "IPA", "Hazy IPA", "Double IPA") counts only alongside that beer's own brewery.
- A name never counts when the label shows a different brewery from our list.
- With the brewery read, a name may match on its distinctive words alone ("VAGABOND" for "Vagabond Pale Ale"), but gluten-free claim words are never dropped, and it must fit only one of the brewery's beers.
- Near-miss reads need an exact anchor (`findWords`); short words must be exact.

A menu (`findMenuCandidates`) can match several beers, and other breweries on it don't count against a name. Names match as whole words only (First Chop's "AVA" matched inside "AVAILABLE"), and may run onto the next line only within a block of text: readers separate blocks with a blank line (ML Kit's blocks; `inBlocks` groups the on-device reader's lines), so a "GLUTEN FREE" heading under "Stella Artois" doesn't make it Stella Artois Gluten Free. A style-only name needs its own brewery within two lines, as a whole word, and not another brewery on the name's own line ("Glutenberg IPA" beside "Omission Lager" isn't Omission's IPA). Menus print short names, so a beer also matches on one line from its brewery plus the rest of its name ("Brewdog Vagabond"): style words may be left out, never gluten-free claims, and a style the line names that the beer's name lacks rules it out. A brewery plus a gluten-free claim is not enough ("Omnipollo Gluten Free, Pilsner" doesn't name Stellaris and gives no match); short names that do identify a beer are listed by hand in `MENU_SHORT_NAMES` ("Peroni Gluten Free").

`__tests__/realScans.test.ts` holds text from real scans, from both ML Kit and Nano, with the expected beer, or `null` for gluten-containing look-alikes. Any matcher change must keep it passing. Add new reports there, especially failures.

**Scan debug mode:** hold the shutter to toggle it. Each photo then opens `app/scan-debug.tsx`, which shows the reader's boxes and text (with ML Kit's reading alongside, when the on-device reader was used), each Nano reading, every candidate with its rejection reason, what a normal scan would do, and a "Share report" for turning a scan into a test.

Recognition must stay on-device (a product decision): no cloud vision or LLM fallback.

## On-device OCR models (`modules/ocr-models`)

PP-OCRv6 small (find and read text lines) and WATERec (artistic lettering, for lines PP-OCRv6 reads with low confidence), run with a minimal ONNX Runtime in Kotlin (`LabelOcr.kt`, a port of PaddleX's pipeline: 960 px, rotated text boxes read straightened). On the 20-photo bench it gets 15 right against ML Kit's 10, at ~0.5 s per photo. Android only for now (iOS would need `LabelOcr.kt` ported to Swift). `glutenless://bench` scans every photo pushed to the app's files dir (`images/`) as a can scan would (`?reader=platform`: with ML Kit), and logs to logcat. `?set=menus` reads the photos in `menus/` with each menu reader instead; `tools/ocr-bench/images/menus/` has 20 menus for it, drawn by `tools/ocr-bench/make_menus.py` and made to look photographed, with gluten-free beers among look-alikes that contain gluten (commands in its `SOURCES.md`), and `tools/ocr-bench/score_menus.mts` scores the readings with the menu matcher (the app finds 26 of the 27 listed beers, none wrong). The can and bottle photos are in `tools/ocr-bench/images/beers/` (not in git).

- The models (~58 MB, shrunk by `tools/ocr-bench/shrink_models.py`: a Latin-only reader, WATERec in 8 bits) are generated, not in git. `install_models.sh` converts them to ORT format and copies them into the module's assets, and `scripts/build-android.sh` refuses to build without them. Files of the same name in the app's external files dir (`onnx/`) take precedence, for testing variants over adb.
- ONNX Runtime is built from source (`tools/ocr-bench/build_ort.sh`, ~20 min, into `modules/ocr-models/android/libs/`, not in git) with only the operators the models use: a few MB instead of the official package's 33. It loads only ORT-format models, pre-optimized at conversion. `install_models.sh` rebuilds it when the models' operator list changes; a model needing an operator the build lacks fails to load, so the reader falls back to ML Kit.
- `tools/ocr-bench` compares readers on label photos through `lib/match.ts` (`bench.py`, then `node tools/ocr-bench/score.mts`). Re-check accuracy there and on the phone after changing models or the pipeline.
- WATERec can invent text on small print ("www.…COM"), like Gemini Nano.

## Gemini Nano module (`modules/label-reader`)

A local Expo module (Kotlin, Android only) around the ML Kit GenAI Prompt API. On iOS and on phones without AICore it reports `unavailable` and the app falls back to OCR. Its dependency forces three build settings, all applied at prebuild by `app.plugin.js` and `expo-build-properties` in `app.json`:
- **Kotlin 2.2.21 for the compiler.** The GenAI libraries are compiled with Kotlin 2.3. `expo-build-properties`' `kotlinVersion` alone doesn't reach the compiler on SDK 57, because React Native's Gradle plugin pulls in 2.1.20, so the plugin pins the classpath.
- **A larger Gradle metaspace.**
- **`minSdkVersion` 26.**

The official `expo-ai` package may eventually replace this module (and add iOS via Apple Foundation Models); its preview didn't support image input on Android.

## Conventions

- Styles use `useStyles(makeStyles)` with `makeStyles = (colors: Palette) => StyleSheet.create(...)` from `lib/theme.ts`, so light/dark palettes are cached per palette. The camera screens are dark in both themes.
- `lib/search.ts` (typo-tolerant list search) and `lib/match.ts` (label matching) are separate. Search tolerates more, since a wrong search result is visible to the person, while a wrong label match is presented as an answer.
- Tests mock native modules: `__mocks__/` (and the `moduleNameMapper` for `expo-sqlite/kv-store` in `package.json`), plus `jest.mock` for ML Kit and `modules/label-reader`.
